# Transport audit — commit `bedb5cf`, 2 September 2026

Four independent reviews of the HSFZ/DoIP/ELM327 transport commit, each briefed to be a harsh
critic rather than a helpful one: byte-level protocol correctness, Android build and integration,
safety and store readiness, and code quality and test coverage.

The commit under review was a self-declared work in progress. Its own message said the build was
expected to fail, and it did: five unresolved references in the connection screen. That much was
known. What the reviews added was the set of defects that would only have shown up with a car
attached.

This document records what was found, what this branch changed, and what is still open. It is
meant to be read before anyone connects the app to a real F10.

---

## The four findings that mattered most

Ranked by what they would have done to a car or a user, not by how hard they were to fix.

### 1. A stale response could be written into the wrong coding block

No transport correlated a response to the request that asked for it. HSFZ checked only that a frame
came from the right module; the OBD path filtered on CAN id alone; `UdsClient` accepted a `0x62`
reply without comparing the identifier it echoed.

The failure needs no unusual conditions. A module takes longer than the read timeout to answer a
coding-block read, so the request fails and its answer stays queued on the link. The user taps the
next item, which is mapped to a different identifier. That request reads the previous answer,
`UdsClient` strips three bytes and returns it, and `CodingEngine` performs read-modify-write using
the contents of the wrong block — then writes the result back. On an FRM3 that is the realistic path
to a module that no longer works.

**Fixed.** Responses are now matched against the request's service id and source module, stale
frames are skipped, the link is drained after any timeout, and `UdsClient` verifies the echoed
identifier on every `0x62`/`0x6E`.

### 2. The OBD path would not have talked to the car at all

Frames were transmitted unpadded, with variable data-length. F-series modules expect a fixed 8-byte
data field and a large share of them silently drop anything shorter. The connect-time handshake
would have failed on most modules, and any that answered would still have failed on segmented
reads, because the flow-control frame was short too.

**Fixed.** Every frame is padded to 8 bytes, and the adapter is configured with `ATSP6` rather than
a user-defined protocol whose option bits clone firmwares interpret inconsistently.

### 3. A frame split across TCP segments desynchronised the link permanently

`readFully` consumes whatever has arrived before it throws on timeout. An ENET-WiFi adapter is a
serial-to-TCP bridge, so a split frame is routine rather than exceptional. Once one had been
half-consumed, every subsequent read interpreted payload bytes as a header, producing bogus lengths
and a socket that stayed "connected" while returning garbage.

**Fixed.** `FrameReader` accumulates into its own buffer and only peeks until a whole frame is
present, so a timeout is recoverable. On an unrecoverable framing error the socket is now closed, so
`isConnected` stops reporting a link that no longer works.

### 4. The connection outlived nothing and the gateway dropped it

Connect ran in the screen's `viewModelScope`. Backing out mid-handshake cancelled the coroutine, but
the blocking socket work continued: the transport connected, started its keep-alive thread, and was
then never recorded — an orphaned session on the gateway plus a daemon thread pinging it forever.
The `CancellationException` was caught by a generic handler and shown to the user as a connection
error reading "Job was cancelled". Separately, the keep-alive never pinged the gateway itself and
expired tracked modules after 60 seconds, so a user sitting on a confirmation dialog would return to
a closed session.

**Fixed.** Connects run on an application-scoped coroutine serialised by a mutex, the gateway is
pinned in the keep-alive for the life of the link, and failures are translated into sentences a
driver can act on.

## Everything that changed on this branch

### Protocol and transport

| Change | Why |
|---|---|
| `FramedTcpTransport` base class | HSFZ and DoIP were the same 150-line class twice. Framing, correlation, timeouts, the response-pending loop and the keep-alive now live once. |
| `FrameReader` | Timeout-safe framed reads (finding 3). |
| Response correlation + drain on timeout | Finding 1. |
| `UdsClient` identifier echo check | Finding 1, at the protocol layer. |
| 8-byte padding, `ATSP6`, `ATCSM0` | Finding 2, plus keeping the gateway's CAN controller acknowledged during monitor mode. |
| Flow-control block size and WAIT honoured | A module asking for 8-frame blocks was previously sent everything at once, truncating a coding write. |
| `ATR1` restored in a `finally` | An exception mid-stream left the adapter in "no replies" mode, so every later request looked like a silent module. |
| Fast answer after `0x78` kept | A module that sends "busy" and then the real answer in the same window had its answer discarded, followed by a 30-second wait for it. |
| Adapter resynchronisation after a timeout | Prevents the ELM equivalent of finding 1. |
| `ATST` shortened to 200 ms | The prompt now returns quickly enough after a first frame that our flow control lands inside the module's ~1 s timer. |
| `IsoTp` guards | A stray consecutive frame threw `NegativeArraySizeException`; malformed lengths are now rejected with a typed error. |
| `LinkNetwork` socket pinning | An ENET or WiFi-dongle network has no internet, so Android routed the connection out the mobile interface and it never reached the car. |
| Discovery over real interface broadcasts + multicast lock | The hardcoded three-address list missed most real subnets, and inbound broadcast replies are filtered without the lock. |
| Keep-alive rewritten | Loops on a flag rather than the interrupt status (a transport swallowing `InterruptedException` left a zombie thread), joins on stop, pins the gateway, and drops modules that keep failing. |
| BLE link fixes | Both `onCharacteristicChanged` overloads fed the buffer, duplicating every byte on Android 13+; MTU and write failures were ignored; bytes were boxed individually into an unbounded queue. |

### Safety

| Change | Why |
|---|---|
| Post-write verification with rollback | The class documentation already claimed writes were verified. They were not. A dropped frame on a clone adapter left a half-applied coding silently in place. |
| `maxRequestLength` enforced | The property existed and was documented as preventing truncation, but had no callers. |
| VIN read on connect, backups stamped with it | Coding bytes are specific to one car. A hardware backup could previously be restored onto a different vehicle. |
| Demo flag taken from the transport instance | It was derived from `LiveData` that lags a thread behind, so a hardware transport could briefly be treated as demo — bypassing the verified-map gate. |
| Local values cleared when hardware connects | After a demo session the app showed simulated values next to a real car. |
| First-run disclaimer | The only warning was a paragraph in the README. |
| `allowBackup=false` + data extraction rules | The database was eligible for cloud backup and restore onto a different phone paired with a different car. |

### Store readiness

Target and compile SDK moved 34 → 36 (Play requires 36 for new apps as of August 2026), which
needed Gradle 8.9 → 8.13 and AGP 8.5.2 → 8.11.1. R8 and resource shrinking are on for release, the
release workflow now also produces an App Bundle, and the version is `1.1.0` (code 3). Unused Wi-Fi
permissions were dropped, Bluetooth is declared optional, and the connection screen's text moved
into resources so it can be translated. The stricter lint that came with the new toolchain caught a
real nullability bug in the diagnostics view model, which is fixed rather than baselined.

### Tests

From 0 tests on the new transport code to **102 tests passing**, covering HSFZ framing and
discovery, ISO-TP segmentation and reassembly including sequence wrap and malformed input, the
ELM327 transport against a scripted adapter (setup, single and segmented exchanges, flow control,
block size, `0x78`, adapter error strings), the keep-alive's lifecycle including the zombie-thread
case, `FrameReader`'s partial-read recovery, the HSFZ transport against a scripted gateway on
loopback, the identifier echo check, and coding write verification and rollback.

## Still open

These are known and deliberate, not oversights. The first three are why the app must not be sold
as a coding tool yet.

1. **The coding catalog is fabricated.** All 26 maps in `codings_f10.json` carry `verified: false`
   and use invented identifiers and offsets. The app refuses to write them to hardware, so it is
   safe — but it means coding has no content until maps are derived from a real car's data. Ship it
   as a diagnostics tool, or with coding disabled, until that changes.
2. **Nothing has been tested against a car.** Every protocol claim here is backed by public
   documentation and unit tests, not by a session with an F10.
3. **`SecurityAccess (0x27)` is not implemented.** Modules that require a seed/key exchange will
   reject coding writes with `0x33`. The failure is clean, but those modules cannot be coded.
4. **No `ECUReset (0x11)` after a write.** Some modules only apply new coding after a reset or a
   power cycle.
5. **The verified-map gate is still a boolean.** It should be a fingerprint compared against the
   module's own hardware and software version read from the car. The VIN binding added here is a
   first step, not the finished mechanism.
6. **Trademark exposure.** The package name `com.bmw.assistant` and the name "BMW Assistant" imply
   an affiliation that does not exist. A package name cannot be changed after publication, so this
   has to be settled before the first upload, not after.
7. **No privacy policy, no crash reporting, no store listing assets.**
8. **Discovery trusts any responder.** ENET-WiFi adapters and OBD dongles run open access points, so
   a reported VIN is a hint for the user to confirm rather than proof of which car answered.
